# Verification harness

Type-checks the whole Kotlin source set without an Android SDK or Gradle. Several
bugs that reached the device would have been caught here.

## Setup (once)

The compiler version must match `org.jetbrains.kotlin.android` in `build.gradle.kts`
(currently 1.9.24). `verify.sh` refuses to run on a mismatch, because 1.9.x is the K1
compiler and 2.0+ is K2, and K2 accepts code K1 rejects — a clean local check against
the wrong compiler is worse than no check.

    curl -L -o /tmp/kotlin.zip \
      https://github.com/JetBrains/kotlin/releases/download/v1.9.24/kotlin-compiler-1.9.24.zip
    unzip -q /tmp/kotlin.zip -d "$HOME"        # -> $HOME/kotlinc

    curl -L -o "$HOME/android.jar" \
      https://raw.githubusercontent.com/Sable/android-platforms/master/android-33/android.jar

## Run

    tools/harness/verify.sh

Exit code 0 and "OK" means clean. Anything else prints the compiler errors.

## What the stubs are

`android.jar` covers the framework, but the app also uses AppCompat, Material and the
aapt-generated `R`, none of which are in it. `stubs/` supplies signature-only versions:

- `stubs.kt`  — `AppCompatActivity`, `AlertDialog` + `Builder`
- `stubs2.kt` — `WindowCompat`
- `stubs3.kt` — Material `Slider`
- `R.kt`      — generated by `gen_r.py` from the real `res/` XML, so a layout id that
                gets renamed shows up as a compile error rather than passing silently

Bodies are empty on purpose. This checks types, not behaviour.

## Confirming the harness is not vacuous

A check that can never fail is worth nothing. Break something deliberately and confirm
it is caught, e.g. pass the wrong type to a function, run `verify.sh`, see it fail,
then revert.
